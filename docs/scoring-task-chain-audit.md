# 总榜、伙伴与大神任务链路审查

## 当前唯一总榜口径

```text
关卡基础分 = Σ round(min(1.2, 单关历史最高原始分 / 该关 starBase) × 1000)
总榜分 = round((关卡基础分 + 无尽历史最高分) × (1 + 伙伴加成率))
```

- 每关最多贡献 1200 分，重复挑战只保留历史最高分。
- 无尽模式只保留历史最高分。
- 榜单只读取 `yanli_rank`，排序字段为 `user_score`；旧 `wujin_rank` 不再被前端使用。
- 伙伴加入、关卡历史最高分提高或无尽最高分提高时，React 会重新计算完整总榜分并写入 `user_score`，不是只在伙伴解锁的一刻加一次固定分。

## 伙伴加成

| 伙伴条件 | 加成 |
| --- | ---: |
| 累计在线 30 分钟 | 1.25% |
| 单日游玩 20 分钟 | 1.25% |
| 发现 15 种自然类素材 | 1.25% |
| 10 关三星 | 1.25% |
| 累计找到 500 件 | 1.25% |
| 累计在线 10 小时 | 1.25% |
| “更新大神 App”任务后台下发 | 2.5% |
| 集齐其余 7 位伙伴 | 5% |
| **全部伙伴合计** | **15%** |

所以基础总分继续增加时，伙伴百分比会始终作用于新的基础总分。例如基础总分从 10,000 增长到 12,000，1.25% 伙伴对应的榜分会从 10,125 自动变成 12,150。

## 大神任务完整链路

1. 首页“大神任务”或伙伴卡“前往大神任务”调用 `openTaskPanel()`。
2. `TaskModule.evoke` 使用同一套 `actId + appKey` 打开真实任务面板，角色绑定仍由大神 SDK 处理。
3. CMS 中“更新大神 App 到最新版本”任务完成后，后台把 `function_partner_latest` 设置为 1。
4. 前端启动、回到前台以及未到账期间每 15 秒读取一次该字段。
5. 只有服务端值大于 0 才解锁该伙伴并计入 2.5%；读取失败时失败关闭，不发伙伴、不加榜分。
6. 集齐其余 7 位后最终伙伴自动解锁，再加 5%；随后完整总榜分重新写入 `user_score`。

`function_addtime` / `function_tishi` 也是后台发放、前端读取；使用时先成功写回余额减 1，再生效。单会话连点有在途锁，但跨设备同时消耗并不是服务端原子扣减。

## 已补的数据安全保护

- 大神环境启动时先读取 `level_detail`、`levelsBaseScore`、`endlessBest`、`user_time`、`user_daily_time`、`totalItemsFound` 等历史值。
- 本地与服务端累计值逐项取最大值，完成水合前禁止写榜分和时长。
- 换设备或清理缓存后，不会再用本地 0 覆盖已有后台成绩。
- `level_detail` 可用于重新计算关卡基础分和复核每一关历史最高分。

## CMS 必须核对

| Key | 默认值 | 仅内部可修改 | 用途 |
| --- | --- | --- | --- |
| `levelsBaseScore` | 0 | 否 | 关卡标准化基础分 |
| `endlessBest` | 0 | 否 | 无尽最高分 |
| `totalItemsFound` | 0 | 否 | 累计寻物 |
| `partnerCount` | 0 | **否** | 前端伙伴数审计镜像；当前截图配置成“是”会导致同步失败 |
| `function_partner_latest` | 0 | **是** | 只允许大神任务后台下发 |
| `level_detail` | `{}` | 否 | 每关历史最高原始分 JSON |
| `user_time` | 0 | 否 | 累计可见在线时长，开启任务统计 |
| `user_daily_time` | 0 | 否 | 当日有效游玩时长，开启任务统计 |
| `function_addtime` | 0 | 否 | 后台发放、前端消耗 |
| `function_tishi` | 0 | 否 | 后台发放、前端消耗 |
| `user_score` | 0 | 否 | `yanli_rank` 唯一排序字段 |

所有字段保持“游客读取不允许”。`yanli_rank` 使用 `user_score` 数值大者靠前、日榜关闭；确认只保留一个榜后可在 CMS 删除或停用 `wujin_rank`。

## 上线前仍需处理的防刷边界

当前分数、普通伙伴条件和在线时长最终仍由客户端上报；`obfuscatedBatchWriteData` 能降低随手改值，但不能防住修改客户端或重放请求。涉及 TOP20 实物奖励时，不能只信 `user_score`。

建议后台增加一个仅内部可写的 `partner_bonus_bps_verified`（0–1500）或等价的伙伴验证状态，并在活动结束时按 `level_detail + endlessBest + 已验证伙伴加成` 服务端重算候选人的最终分。若还要求跨设备完整还原“具体解锁了哪几位普通伙伴”，需再增加 `partner_state`（JSON）或逐伙伴字段；目前 `partnerCount` 只能同步数量，不能还原具体伙伴。
