## Context

`ds-act-sdk` 接入 Skill（MODE 6）由一个编排器（`ds-act-sdk.md`）和三个子模块（`act-task.md`、`act-task-checker.md`、`act-cps-bar.md`）组成。当前设计中，用户配置收集分散在编排器步骤 3 和各子模块的早期步骤里；子模块承担"问配置 + 生成代码"双重职责；`frontId` 在多个子模块中独立检查，存在重复询问风险。

## Goals / Non-Goals

**Goals:**
- 所有用户配置收集集中到编排器的单一步骤中
- 子模块职责单一化：仅负责按已有参数生成代码
- `frontId` 在整个流程中最多询问一次
- 修正 SKILL.md 与 act-task-checker.md 之间关于 `tc.query()` 的矛盾描述

**Non-Goals:**
- 不修改任何生成代码的内容或逻辑（骨架代码、模板代码不变）
- 不改变用户最终得到的代码结果
- 不改变子模块的加载机制（仍由编排器按 A→B→C 顺序加载）

## Decisions

### 决策 1：在编排器中新增「集中收集配置」步骤

**方案选择：** 在步骤 4（功能多选）之后插入新步骤 5「按需收集配置参数」，按用户选择逐项询问。

**理由：** 用户选完 A/B/C 后立刻知道需要什么配置，一次性问完符合认知流程，避免在代码生成过程中反复打断。

**替代方案：** 保持现状（分散在子模块中问）— 已知问题：`frontId` 重复询问、子模块职责不纯。

---

**新步骤 5 收集逻辑：**

```
选了 A（任务面板）→
  1. 面板触发方式：[A] 自动按钮 / [B] 已有元素
  2. （B 触发）描述触发元素 → 提取选择器
  3. showRole：Y / N
  4. 是否有 CPS 下载任务？Y / N
     └── Y → 检查 frontId 是否已填 → 未填则询问

选了 B（回流任务）→
  1. asId（任务 ID）
  2. 触发时机：[A] 登录后自动 / [B] 点击触发 / [C] 手动调用
     └── B 触发 → 描述触发元素 → 提取选择器

选了 C（CPS 通用悬浮栏）→
  1. 检查 frontId 是否已收集（A 步骤中收集过则跳过）
     └── 未收集 → 询问 frontId
```

### 决策 2：子模块重构为纯代码生成

子模块中所有 Q&A 步骤移除，各子模块文件头部新增「**依赖参数**」说明，列出编排器步骤 5 已收集好的参数名，子模块直接使用这些参数生成代码。

| 子模块 | 移除步骤 | 保留步骤 |
|--------|---------|---------|
| act-task.md | A.1（触发方式）、A.2（frontId 检查）| HTML 容器、代码生成、占位符填充 |
| act-task-checker.md | B.2（配置问答）| API 说明（更新）、代码生成、占位符填充 |
| act-cps-bar.md | C.1（frontId 问答）| HTML 容器、代码生成 |

### 决策 3：act-task-checker.md B.1 措辞更新

`query()` 的当前说明与代码示例矛盾。统一为：

> `isCompleted` / `isClaimable` 是 async 方法，内部会自动处理初始化，**无需 `query()` 预热**。若需获取任务详情列表（如空值判断），可主动调用 `await tc.query()`。

代码示例（B.3）保持不变——其中调用 `tc.query()` 是为了空值检查，行为正确。

### 决策 4：步骤 3 移除 frontId

当前步骤 3 将 `frontId` 标记为可选并提前收集。新设计将 frontId 完全移到步骤 5 按需收集，步骤 3 只保留 `actId` 和 `appKey`（两者都必填）。

## Risks / Trade-offs

- **子模块可读性降低** → 子模块文件头部新增「依赖参数」说明，明确列出从编排器传入的变量，保证文档自洽
- **编排器步骤 5 内容变长** → 按选择项分节呈现（A / B / C 各一块），结构清晰不堆砌
- **步骤编号变更** → ds-act-sdk.md 步骤 5/6/7 重新编号，SKILL.md 常见问题涉及步骤编号的引用需同步检查
