## Context

当前路由"直接匹配即执行"，新用户看不到能力全貌、无工作流引导。需轻量补充菜单展示 + 链式推荐，同时修正 [5] 依赖错误。本 change 刻意避免重设计——不引入状态机、单选契约死规则、交互措辞规定。

## Decisions

### 决策 1：菜单有条件展示，非每次强制

首次触发或意图不明确时展示菜单；用户明确指定能力（"帮我接入大神"/"模式1"）时可直接执行。理由：熟悉用户每次强制弹 10 行菜单是冗余仪式；菜单是"提供全貌"的手段，不是"每次必弹"的仪式。备选"每次强制展示"放弃——对明确意图用户冗余。

### 决策 2：状态仅标"已具备"二态，不做 4 态推断规则表

菜单状态列仅标 `✅ 已具备`（前置扫描检测到产物，如 [1] 检测到 DS Marker）。其余不标——agent 根据依赖列 + 扫描结果自然判断是否可执行，必要时在描述里提"需先 [1]"。理由：4 态枚举（⏳/⚠️/🔒/✅）+ 13 行规则表把 agent 当无判断力状态机，过重，且曾导致三向不一致。二态 + agent 判断足够。备选"4 态规则表"放弃——过重。

### 决策 3：推荐一句话 + 推荐路径，不穷举场景

每个主流程能力完成后重新展示菜单 + 推荐路径里的下一步（一句话）。[7]/[C] 工具能力不强制推荐。理由：7 类推荐场景穷举过重；推荐路径 `[0]→[1]→[扩展]→[2]→[3]` 本身已表达主线，agent 自然推导。备选"7 类穷举"放弃——过重。

### 决策 4：菜单模板作示例非 MUST

菜单 Markdown 表格是示例，agent 可照画或用自然语言展示全貌。理由：四列格式 MUST + 顺序不可颠倒把 agent 自然交互僵化。备选"格式 MUST"放弃——僵化。

## Risks

- 菜单有条件展示可能让 agent 不确定"何时算意图明确" → 缓解：明确指定（编号/能力名）即算明确，其余展示。
- 状态二态可能信息量不足 → 缓解：agent 在描述里提"需先 [1]"补充。
