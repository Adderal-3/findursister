# Spec: ds-act-workflow Git 管理门禁

> 本 spec 由 grill-with-docs 会话综合而成,遵循 to-spec 模板。术语取自 `CONTEXT.md`,架构决策见 `docs/adr/0001-git-management-gate.md`。经用户确认不发布到 issue tracker,作为本地文件随分支演进。

## Problem Statement

ds-act-workflow 处理的 H5 活动大多数未纳入 git,而技能对 H5 活动的文件做原地破坏性改动(规范目录覆写 HTML、注入改 JS、部署打包),没有任何撤销路径。开发者一旦让技能跑过,既无法回退到技能介入前的状态,也无法看清"技能到底改了什么、何时改的"。同时,因为 H5 活动普遍没有 git,技能碰过的页面也谈不上"被版本管理规范过"。

## Solution

在 ds-act-workflow 路由器中引入一个跨切**门禁**:任何改源码的能力执行前自动"确保 git + 基线",执行后自动按约定格式提交。非 git 的 H5 活动自动 init + 基线;已在仓库内的复用;位于父仓库子目录的门禁不介入。只管本地,不 push。这让每一次技能改动都可回退(基线)、可追溯(能力提交)、且确保被碰过的 H5 活动都纳入了 git(规范)。

## User Stories

1. 作为 H5 活动开发者,我希望技能在改动我的文件之前先打个基线快照,这样即使技能改错了,我能一键回退到技能介入前的状态。
2. 作为 H5 活动开发者,我希望技能跑完一个能力后自动提交,这样我能用 git log 看清技能每一步改了什么。
3. 作为 H5 活动开发者,我希望技能提交带 `(ds-act-workflow)` 标记,这样我能把"技能产生的提交"和"我自己写的提交"区分开。
4. 作为 H5 活动开发者,我希望我的 H5 活动目录如果不是 git 仓库,技能自动帮我 init,这样我不用先手动 git init 才能用技能。
5. 作为 H5 活动开发者,我希望技能不会把 node_modules、dist、deploy.zip 这些可再生产物提交进库,这样仓库保持干净、只跟踪源码。
6. 作为 H5 活动开发者,我希望技能在已有仓库里运行时复用我的仓库,而不是新建一个,这样不破坏我已有的 git 历史。
7. 作为 H5 活动开发者,当我的仓库有未提交改动时,我希望技能先把它们存成基线再动手,这样我的临时改动不会丢、也不会和技能的改动混在一起。
8. 作为 H5 活动开发者,当我的 H5 活动位于某个大仓库的子目录时,我希望技能别往父仓库里写东西,这样不污染父仓库历史。
9. 作为 H5 活动开发者,当某个能力跑到一半失败时,我希望技能把半成品状态存下来并标注"中断",这样我能检查现场、决定是回退还是继续。
10. 作为 H5 活动开发者,当某个能力跑完发现没有任何改动(幂等重入)时,我希望技能不要产生空提交,这样历史保持干净。
11. 作为 H5 活动开发者,我希望只读能力(如审查)不会触发 git 提交,这样审查不会在历史里留噪音。
12. 作为 H5 活动开发者,我希望只产出打包产物的能力(如部署)不触发 git 提交,因为产物本来就 gitignore 了。
13. 作为 H5 活动开发者,我希望技能的 git 管理只在本地进行、不 push,这样推送时机由我掌控。
14. 作为技能维护者,我希望门禁是路由器基础设施、不可被用户跳过,这样"规范"才真正落地——每个被碰过的 H5 活动都必然纳入 git。
15. 作为技能维护者,我希望门禁逻辑集中在一处,这样检测矩阵、提交格式、scope 规则改一处就全局生效。
16. 作为技能维护者,我希望门禁与能力契约解耦(能力文件不必各自实现 git 逻辑),这样新增能力时不用重复写 git 代码。
17. 作为技能维护者,我希望门禁的检测矩阵覆盖四种仓库状态(gitless / 干净 / 脏 / 父仓库子目录),这样不同入口场景都行为正确。
18. 作为技能维护者,我希望基线提交和能力提交用不同的消息模板,这样在 git log 里能一眼区分"技能介入前快照"和"某能力的产出"。
19. 作为技能维护者,我希望门禁在能力失败时保留现场而非自动回退,这样最坏情况下信息不丢、用户能自主决策。
20. 作为技能维护者,我希望门禁建在契约分支(feature/contract-soft-deps-faq)之上,这样与未来架构对齐、合并时无需搬迁。

## Implementation Decisions

- **形态:跨切门禁,非独立能力。** 门禁是路由器级基础设施,在任何能力执行前(ensure+基线)与后(提交)自动运行,不可被用户跳过。不落进 primitive/capability/contract/audit 任一层,待在路由器里,与现有前置扫描同层。
- **驱动**:安全/回滚(基线)+ 规范(不可跳过的 git 强制)+ 可追溯(能力提交)。部署溯源明确排除(部署不打 tag、不绑 commit)。
- **检测矩阵(ensure+基线段)**:
  - 无 .git → auto-init + 提交全部文件为基线。
  - .git 在目标根 + 工作区脏 → 复用仓库 + 把未提交改动提交为基线(使工作区干净)。
  - .git 在目标根 + 工作区干净 → 复用仓库,HEAD 即基线,跳过基线提交。
  - .git 在祖先目录(父仓库子目录)→ 门禁不介入,能力照常跑(不建 .git、不提交)。
  - 检测手段:判断 .git 目录落在目标根还是祖先目录。
- **.gitignore 策略**:auto-init 时写 .gitignore,排除 `node_modules/`、`dist/`、`deploy.zip`、`.skill-cache.json`、dev-server 证书(`*.pem`/`*.crt`/`*.key`)、OS 垃圾(`.DS_Store`/`Thumbs.db`)。只跟踪源码。已有仓库不覆盖用户 .gitignore;若检测到 node_modules 被跟踪则告警。
- **scope(哪些能力触发门禁)**:对改源码的能力全介入——规范目录、Cocos Vite、注入、埋点、持久化、活动SDK、广告预览。对只读或只产 gitignored 产物的不介入——审查(只读)、部署(只产 deploy.zip+dist)、开发服务器(只起服务+产证书)。
- **提交粒度与格式(能力后提交段)**:每个能力一次提交;能力未产生改动(幂等重入)→ 跳过,不产生空提交。格式:`<type>(ds-act-workflow): <中文摘要>`,type 取 feat/refactor/fix 等。`(ds-act-workflow)` scope 是追溯钩子,`git log --grep "ds-act-workflow"` 可捞出全部技能提交。基线提交用专门模板(如 `chore(ds-act-workflow): 基线提交(技能介入前快照)`),与能力提交区分。
- **失败处理**:能力执行中途失败 → 把 partial 状态提交,消息标注 `[中断]`(如 `chore(ds-act-workflow): [中断] inject 部分执行,保留现场`)。回退始终可用(baseline 在)但不自动——把选择权交回用户。
- **范围**:只管本地,不 push。远程推送是用户/人工的事。
- **幂等性**:重入检测——已有基线(工作区干净、HEAD 为技能已知基线)→ 不重建;能力无改动 → 跳过提交;能力有改动 → 新提交。
- **工程落点**:建在 `feature/contract-soft-deps-faq`(契约结构)之上,新分支 `feature/add-git-management`。门禁逻辑写进路由器(与前置扫描同层)+ 一份门禁契约参考文档(描述检测矩阵/.gitignore/提交格式/scope/失败/幂等)。门禁与能力的耦合(scope 哪些能力触发)中心化在门禁契约文档与路由器段;本分支已删除能力的"组合"段,门禁是路由器级自动运行,无需 per-capability 标注。
- **与现有架构的关系**:门禁复用契约架构的四层分层;它本身是路由器级关注点,不新增"层"。前置扫描已是同类跨切关注点的先例,门禁与之并列。

## Testing Decisions

- **好测试的标准**:只测门禁的可观测外部行为(.git 是否创建、有哪些 commit、commit 消息格式、工作区是否干净),不测内部实现细节。门禁是行为驱动的(状态矩阵 → 可观测副作用),天然适合行为测试。
- **测试缝隙**:单一缝隙——通过既有 eval 系统在一个 H5 fixture 上跑一个能力,观察门禁副作用。不新增缝隙(理想:一条)。
- **覆盖场景(8 个,全部在单缝上可观测)**:
  1. gitless fixture → 跑 mutating 能力 → 断言:.git 创建、基线 commit 存在、能力 commit 在后、消息含 `(ds-act-workflow)`。
  2. 干净仓库 fixture(③) → 跑 mutating 能力 → 断言:无新基线 commit、能力 commit 在后。
  3. 脏仓库 fixture(②) → 跑 mutating 能力 → 断言:脏改动成基线 commit、再能力 commit。
  4. 父仓库子目录 fixture(④) → 跑 mutating 能力 → 断言:无 .git 创建、无 commit、能力照常完成。
  5. mutating 能力(注入) → 断言:前有 ensure+基线、后有 `(ds-act-workflow)` commit。
  6. 只读能力(审查) → 断言:门禁不介入、无新 commit。
  7. 能力中途失败 → 断言:partial 以 `[中断]` 标注 commit。
  8. 幂等重入(同能力再跑一次无改动)→ 断言:不产生空 commit。
- **既有先例**:eval 系统是仓库唯一的测试设施,既有能力(注入/审查/部署 等)均有 eval 覆盖,新增门禁 eval 沿用同一 fixture + 断言模式。

## Out of Scope

- **部署溯源**:部署不打 tag、不把 deploy.zip 绑回 commit(驱动 4 明确排除)。
- **远程 push**:门禁不 push,不配置远程仓库、不处理认证/命名策略。
- **改写已有仓库的 .gitignore**:已有仓库的 .gitignore 不覆盖,仅告警。
- **monorepo 子目录的 git 管理**:父仓库子目录(④)门禁不介入,不提供 nested repo init 等方案。
- **跨能力的原子性/事务**:多个能力组合执行时不提供"全部成功才提交、否则全回滚"的事务语义;每个能力独立 ensure+提交。
- **门禁的关闭开关**:门禁不可跳过(规范要求),不提供 opt-out。
