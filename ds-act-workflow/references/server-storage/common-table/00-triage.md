# 公共表接入 · 第 0 步：需求识别（Triage）

> 目标：判断运营的这个小游戏项目**是否需要公共表（datahub-table）**，并在需要时引导进入公共表接入流程。
> 定位：三种进入方式——① 5.0 菜单直接选 `[C]`（**独立接入**，本地存档项目或未接存储项目也走这里）；② 用户维度存储（5-B）审查通过后**自动触发一次**；③ 从 5-B 完成菜单手动选 [8]。无论从哪进，本步都会做「基础设施就绪 + 登录态」前置检查。

---

## 0.1 什么是公共表（先分清和用户存储的区别）

| | 用户维度存储（已有） | 公共表 datahub-table（本流程） |
|---|---|---|
| 数据归属 | 挂在**当前登录 uid** 名下，每人一份 | **无主**，一份数据大家共写共读，`__create_uid` 只记录"谁创建的" |
| 典型接口 | `obfuscatedWriteData` / `batchReadData` | `tableUpdate` / `tableFindList` / `tableIncrNumber` … |
| 读别人数据 | 只读（`queryUid` + `allowGuestRead`） | 可读**可写**（人人可投稿/评论/点赞） |
| 查询能力 | 按 key 取值，无条件查询 | conditions + sorts + 分页 |

**判定内核（唯一标准）：**

> 项目里是否存在「**多人共写共读、不按读者 uid 分片**」的数据？

只要有，就需要公共表；只是排行榜那种"只读聚合"不算（用现有 billboard 即可）。

---

## 0.2 开放式识别（不要用封闭清单）

⚠️ 运营同学生成的小游戏代码我们事先并不知道，**不能只靠关键词匹配**。正确做法：

1. **先读懂这个项目实际在做什么**——扫描业务代码、页面结构、交互，理解它的玩法。
2. **再结合它的真实业务**判断是否存在"多人共写共读"的数据。
3. **然后询问用户**是否需要接入公共表（见 0.5），由用户拍板。

下面这串**仅作扫描启发**，命中任一即应提高警觉、主动向用户确认，**但它不是封闭清单**——不在清单里、只要符合判定内核，同样要识别出来：

```
帖吧 / 广场         投稿、发帖、动态墙
评论 / 留言 / 弹幕   任何人对内容追加文字
点赞 / 顶 / 热度     多人对同一条内容累加计数
UGC 展示墙          玩家作品/图片/昵称互相可见
全服共创 / 拼图      大家一起往同一目标累积
晒单 / 战报分享      玩家把结果发到公共区
投票 / 众筹进度      多人对同一选项累加
世界 boss / 全服计数  共享计数器
… （以上仅示例，凡"多人共写共读、非 uid 分片"皆算）
```

**反例（不需要公共表）：** 个人存档、个人最高分、个人已解锁关卡、只读排行榜——这些走用户维度存储或 billboard。

## 0.3 基础设施就绪前置（SDK + gameId，必做）

公共表所有 `table*` 接口都跑在 `mini-game-data-sdk` + `setGameId(miniGameId)` 之上。进入接入前先判断这套基础设施从哪来，避免独立接入时漏配 SDK 或漏填 gameId：

- **项目已有 `game-server-storage.js`**（走过 5-B）→ SDK 已注入 `<head>`、`setGameId` 已调用，**直接复用，无需再问**。代码生成时删兜底段（见 `04-code-gen.md` 4.2）。
- **项目没有 `game-server-storage.js`**（独立接入）→ 需要补两件事，缺一不可：
  1. **拿 miniGameId**：向用户要测试 `devMiniGameId` + 正式 `proMiniGameId`（在小游戏管理后台配置游戏实例后获取）。**用户拿不到就暂缓**——没有 gameId，SDK 路由不到数据表。
  2. **注入 SDK**：把 `mini-game-data-sdk` 的 JS 注入含 DS Marker 的 HTML `<head>`（版本 ≥ `0.2.1`，`0.2.0` 起不再引入 `index.css`，资源地址见 `99-api-reference.md`）。
  
  这两件事在第 4 步 `04-code-gen.md` 落地：miniGameId 填进 `game-common-table.js` 兜底段的 `GAME_ID_CONFIG`，SDK 注入 `<head>`。triage 阶段先确认用户能提供 miniGameId。

---

## 0.4 登录态前置检查（必做）

公共表每条记录都会写入内置字段 `__create_uid`（创建人 UID），**依赖登录态**。进入流程前确认：

- 项目已接入登录（`window.dsLogin.hasLoggedIn()` / `ds.callHandler('checkLogined')` 等登录能力存在）。
- 写操作（`tableUpdate` / `tableIncrNumber` / `tableDelete`）由点击触发时，同用户存储一样应有登录态保护（`withPrecheck` 包裹）。

若项目**没有登录态**：提示用户"公共表依赖登录（用于记录 `__create_uid` 与权限判定），需先接入登录能力再接公共表"，暂缓进入。

## 0.5 询问用户

识别到疑似公共表需求后，输出：

```
检测到你的项目里可能有「多人共写共读」的数据：
  · [具体业务，如"广场投稿 + 评论 + 点赞"]

这类数据不属于某个玩家个人，适合用「公共表（datahub-table）」来存。
是否需要接入公共表功能？

  [Y] 需要，进入公共表接入流程
  [N] 不需要，跳过
```

- **用户选 Y** → 先确认 0.3（基础设施就绪）与 0.4（登录态）都通过，再进入第 1 步 `01-table-design.md`（表/字段/权限位设计）。
- **用户选 N** → 结束本流程（从 5-B 自动触发/菜单进入的回到 5-B 完成菜单；独立接入的直接结束）。

> 若识别不确定，宁可**问用户**，不要自作主张。运营最清楚自己项目要什么。
