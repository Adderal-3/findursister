# 用户维度存储 · 第 2.5 步：生成 storage-keys.d.ts 类型声明（轻量）

> 目标：把第 1 步锁定的「字段表」（recordKey / SDK 类型 / 序列化列）转成一份轻量 TypeScript 声明 `storage-keys.d.ts`，放 `src/` 目录（与 `game-server-storage.js` / `game.js` 同级）。
> 前置：第 1 步字段表已锁定（`00-intake.md` 1.4）。
> 后置：第 3 步生成 `game-server-storage.js` 读写代码时**对照本文件比对每个 recordKey 的值类型**，尤其 `*_LIST` 不能 `JSON.stringify`、存 JSON 的 `string` key 必须 stringify/parse 配对。

---

## 2.5.1 为什么用户存储也要这一步

用户维度存储的 key 类型只有 6 种、**没有 OBJECT 类型**（与公共表一致）：
`STRING / NUMBER / BOOLEAN / STRING_LIST / NUMBER_LIST / BOOLEAN_LIST`（见 `../json-key-comment.md`）。

所以同一类"类型踩坑"会复现：
- 把 `STRING_LIST` 值 `JSON.stringify` 后再写（应**直传数组**）——服务端 listRules 逐项校验会错位。
- 把嵌套对象 / 对象数组塞进 `STRING` key 却忘了 `JSON.stringify`（读时忘了 `JSON.parse`）——存进去变 `[object Object]` 或读出来是字符串。
- 写入值的 JS 类型与注册的 `type` 不符（数字存成字符串等）——`dict/save` 校验失败或 valueType 冲突。

用户存储是**扁平 key→value**（一个 key 一个值），比公共表 record 简单，所以只需**一个 `UserStorageKeys` interface** 把每个 recordKey 映射到类型即可，不需要每表一个 interface。这就是"轻量版"。

为什么用 `.d.ts` 而非 `.ts`：见公共表 `common-table/03.5-table-d-ts.md` 2.5.1——纯类型声明、构建工具不编译、IDE 自动加载、非 TS 项目零风险、不需 import。

---

## 2.5.2 生成规则

1. **文件位置**：`src/storage-keys.d.ts`（与 `game-server-storage.js` / `game.js` 同级）。若项目无 `src/`，则放项目根目录，与 `index.html` 同级。
2. **单个 interface** `UserStorageKeys`，每个字段名 = 字段表里的 `recordKey`，类型按下表映射，值来源用行内注释标出。
3. **SDK 类型 → TS 类型映射**：

   | 字段表 SDK 类型 | TS 类型 | 说明 |
   |---|---|---|
   | `number` (NUMBER) | `number` | |
   | `string` (STRING) | `string` | 若该 key 存的是 JSON（序列化列标了 `JSON.stringify`），TS 里写成具体结构类型（如 `Building[]`）并注明"存 string、写前 stringify、读后 parse" |
   | `boolean` (BOOLEAN) | `boolean` | |
   | `number[]` (NUMBER_LIST) | `number[]` | **直传数组**，禁止 stringify/parse |
   | `string[]` (STRING_LIST) | `string[]` | 元素是纯字符串。**直传数组**，禁止 stringify/parse |
   | `boolean[]` (BOOLEAN_LIST) | `boolean[]` | 同上 |

   > ⚠️ 字段表里"序列化列 = JSON.stringify"的字段（如 `buildings_json`），实际注册类型是 **STRING**，不是 `*_LIST`。TS 里标成具体结构 + 注明存 JSON，提醒 AI 读写时 stringify/parse 配对。**别把它标成 `Building[]` 却当数组直传**。

4. **默认值可选性**：字段表有默认值的 key 视为必有值（不加 `?`）；确实可能缺失的加 `?`。
5. **文件顶部注释**：写明"类型声明、非可执行代码、不需 import；供 AI 生成读写代码比对 recordKey 值类型、IDE 提示用"。

## 2.5.3 模板

```typescript
/**
 * storage-keys.d.ts — 用户维度存储 recordKey 类型声明（轻量）
 *
 * 本文件为 TypeScript 声明文件（.d.ts），非可执行代码：
 *   - 项目不需要 TypeScript / tsconfig / 任何构建改动
 *   - 不需要在任何 .js 里 import
 *   - 供 AI 生成 game-server-storage.js 读写代码时比对每个 recordKey 的值类型
 *   - 供 IDE 提供 IntelliSense
 *
 * 生成依据：第 1 步锁定的字段表（00-intake.md 1.4）
 * 字段表变更后必须同步更新本文件。
 *
 * ⚠️ 用户存储无 OBJECT 类型：嵌套对象/对象数组只能用 STRING key 存 JSON.stringify，读后 JSON.parse。
 */

/** 单个建筑（buildings_json 存为 JSON 字符串，读写时 stringify/parse） */
export interface Building {
  id: string;
  count: number;
}

/** 全部用户存储 recordKey → 值类型 */
export interface UserStorageKeys {
  bake_num: number;            // NUMBER, 当前点数
  lifetime_points: number;     // NUMBER, 历史总点数（排行榜字段）
  prestige_level: number;      // NUMBER, 飞升等级
  unlocked_levels: string[];   // STRING_LIST ← 直传数组，禁止 JSON.stringify
  buildings_json: Building[];  // 存为 STRING：写前 JSON.stringify(Building[])、读后 JSON.parse ← 用户存储无 OBJECT，嵌套结构统一 STRING 存 JSON
  last_save: number;           // NUMBER, 最后存档时间戳
}
```

> 以上为**示例结构**，Agent 须根据第 1 步实际锁定的字段表生成，禁止照抄示例字段名。

## 2.5.4 生成后的自检

1. **每个 `recordKey` 都在 `UserStorageKeys` 里**，字段名与字段表 `recordKey` 完全一致。
2. **`*_LIST` 字段标成 `number[]`/`string[]`/`boolean[]`**，且注明"直传数组、禁止 stringify"。
3. **序列化列标了 `JSON.stringify` 的 key**，TS 标成具体结构类型 + 注明"存 STRING、stringify/parse 配对"，**不是**裸 `string[]`。
4. **值类型与字段表 SDK 类型一一对得上**（别把 number 标成 string）。

自检通过后进入第 3 步代码生成（`02-best-practices.md`），生成读写时对照本文件。
